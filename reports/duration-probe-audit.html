Summary

A boundary-editor bug report — "I can't see the end marker" — traced back to 08 - Slow Ride.mp3 being stored as 4:54.7 long when it actually decodes to 3:58.7. That's not encoder rounding; it's a systematic failure mode: MP3s encoded without a valid Xing/VBR header cause every duration-probing tool in this pipeline to fall back to a bitrate estimate, silently, with no error — and files.duration_ms is documented as decoded, not header-claimed for exactly this reason.

This was already found once. [GDE-FEX-106] measured a 29.2% error rate against the migrated library in 2026 and shipped repair_durations.py to fix it. Re-measuring against real decoded audio rather than another header estimate finds the same 29.7% error rate persists today — because the repair tool checks the stored value against ffprobe's own estimate, which is the same flawed method, so it can never disagree with a wrong value it would have produced itself. Every one of the 1,695 files found this way is invisible to the tool built to catch this class of bug.

Root cause

Three independent call sites ask ffprobe -show_entries format=duration for a file's length: tools/ingest_folder.py (original ingest), tools/extract_library.py (feature extraction), and tools/repair_durations.py (the existing fix). For a well-formed CBR file, or a VBR file with a proper Xing/Info header, this is fast and accurate. For a VBR file without one, ffprobe warns on stderr — Estimating duration from bitrate, this may be inaccurate — and returns a number derived from file_size / average_bitrate, which assumes constant bitrate on a file that, by definition, doesn't have one.

Nothing downstream sees that warning. The estimate comes back shaped exactly like a real duration — a plausible float, no error flag — and is written to files.duration_ms as fact.

Findings, by consequence

criticalplayer/src/queue.rs — real-time playback

The crossfade/lead-out trigger silently loses its fade on affected passages

should_admit() decides when to start the next track from current.duration_ms() = end_ms − start_ms — the same corrupted database value, not the decoder's actual remaining audio. When real content runs out first, PassageDecoder degrades gracefully (clean EOF, no crash), and admit_due()'s (Some(_), None) => true fallback does self-heal within about one tick — so there's no silence gap or hang. But the crossfade window computed from overlap_ms is never reached before real audio ends, so the intended lead-out ramp and the overlap into the next track are both skipped. The track just stops, and the next one starts cold. Confirmed happening on 56 real passages today, every time they play.

hightools/repair_durations.py — the existing fix, disabled by its own method

The repair tool cannot see any of this class of error

Its own probe is ffprobe format=duration — identical to what (almost certainly) produced the wrong value in the first place. Checked directly: of the 1,695 files found wrong against real decoded audio, ffprobe's own re-check agreed with the stored value in all 1,695. A tool comparing a number against the method that generated it will never find a disagreement, regardless of how many times it's run.

mediumtools/suggest_release.py — MusicBrainz matching

Track-length is a scoring signal, fed a number that can be wrong by minutes

delta = abs(f["duration_ms"] - track["length"]) compares the (possibly corrupted) stored duration against MusicBrainz's own track length to help pick the right release. A large, silent error here doesn't crash anything — it just biases matching against the correct release, or toward a wrong one, for exactly the files most likely to need this tool's help (self-published or oddly-encoded audio).

process gap

Zero test coverage on the entire duration-probing surface

No test file exists for ingest_folder.py, extract_library.py's probe_duration_ms, or repair_durations.py. And the repair tool has never been wired into any automated job — it's pure manual CLI, so even a corrected version depends on someone remembering to run it.

Toward a remediation plan

Not yet acted on — findings only, laid out in the order a fix would actually need to happen.

  1. 1Replace the probe itself, once, shared. A real-decode measurement (ffmpeg -progress pipe:1, reading out_time_us) costs about the same wall-clock as the existing ffprobe call is fast — milliseconds to low seconds per file — against extraction work that already takes ~27s/file. One function, used by all three call sites, not three copies to keep in sync.
  2. 2Re-run the corrected repair against the live library, --write, and extend it to invalidate the now-stale lowlevel_cache rows it orphans rather than leaving that gap open a second time.
  3. 3Add the missing test coverage — at minimum, a fixture VBR file with no Xing header, proving the corrected probe gets the real answer and the old one doesn't.
  4. 4Decide whether should_admit should also become independent of the stored duration_ms (defense in depth against whatever the next data-quality surprise turns out to be), or whether closing the data bug at the source is enough on its own.
  5. 5Decide whether re-probing belongs in the regular induct/reanalyze pipeline, or stays a documented manual step after any bulk ingest.
Methodology: full-library scan via ffmpeg -progress pipe:1 (16 parallel workers, 5,709 files, 527s wall time, 0 unreadable) cross-checked against ffprobe format=duration on the 1,695 confirmed-wrong files. Read-only throughout — no writes to data/lempi_new.db.
