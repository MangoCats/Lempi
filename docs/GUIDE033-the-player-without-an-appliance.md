# GUIDE033: The Player Without an Appliance

**Development Guidance — what `lempi-player` assumes about the machine it runs on, and the structural changes that let a phone target be maintained beside the Pi and the desktop without destabilising either**

Written 2026-09-24, after `lempi-core` was split out `[GDE-AND-045]` and before any Android code exists. Every figure below was measured on that date or cites where it was. *Revised the same day after review: two counts, four citations and three claims were wrong, and §3 now reconciles with SPEC011, `[SPEC-PL-065]` and `[GDE-FBD-090]`. §6 records the decisions `[GDE-HST-040]` and `[GDE-HST-050]` needed, all nine accepted by the maintainer on 2026-09-24.*

> **Related:** [GUIDE004](GUIDE004-phone-port-strategy.md) (which route onto a phone, and why) · [GUIDE006](GUIDE006-director-as-a-guest.md) (the `Playback` seam) · [SPEC011](spec/SPEC011-audio-path-supervisor.md) (the path supervisor) · [GUIDE031](GUIDE031-where-an-option-gets-its-value.md) (option layers) · [CLAUDE.md §10](../CLAUDE.md) (the commit gate)

## 1. The dependency a phone actually has

**`[GDE-HST-010]` A phone links `lempi-player` with the appliance parts switched off — not `lempi-core` alone.** GUIDE004 was written assuming the audio path would be rebuilt on Media3 or AVAudioEngine. It may not need to be: `cpal` 0.18.2 carries an AAudio backend (`src/host/aaudio`) with Android-only dependencies (`ndk`, `ndk-context`, `jni`), and `symphonia`, `rubato` and bundled SQLite are portable. If that holds, the decoder, mixer, fades and engine — the hardest and best-measured code here — run on a phone unchanged. **It is a hypothesis until `[GDE-HST-030]` compiles it**: nothing in this repository has yet been built for Android.

That changes what preparation means. **Core should not grow in scope.** Its value is its boundary — 30 crates, none of them audio, web or platform code — and the gate in `build/verify-targets.sh` enforces it. A dependency such as a hash crate for `[GDE-HST-080]` is a different question, which that gate answers. The work is making `lempi-player` indifferent to what kind of machine hosts it.

## 2. What the player assumes about its host

**`[GDE-HST-020]` Four assumptions, each true on every node today and false on a phone:**

| It assumes | Evidence, measured 2026-09-24 |
| :--- | :--- |
| **The player is a binary** | `player/src/bin/lempi.rs` is `#[tokio::main]` with a ~320-line `engine_thread` that opens the session, builds the engine, attaches MPD and runs the loop. `station.rs` repeats a subset. A JNI or UniFFI host has nothing to call. |
| **stdout reaches a journal** | 422 `println!`/`eprintln!` in the player crate — **82 in the library**, 340 in the binaries, most of those program output — and no logging facade. On Android an app's stdout and stderr are discarded, and a phone links the library, not the binaries. |
| **Linux tools exist** | `path.rs` runs `wpctl` every `WATCH` interval while playing, on every build; `bluetooth.rs` runs `sudo -n /usr/local/bin/lempi-btctl`, a privileged helper; the web layer serves LED, Wi-Fi, radio and power routes — `sudo systemctl poweroff` among them — to Windows builds too. |
| **Audio is a path** | The decoder opens with `File::open(path)`, and so do `tags.rs`, `covers.rs` — which also reads the files *beside* the audio for cover art — `lyrics_sidecar.rs`, which writes beside it, `backup.rs`, and relink's hash in core. Android's Storage Access Framework hands out descriptors, and a single-document grant does not reach the folder around it — `[GDE-AND-070]`'s open question. |

**`[GDE-HST-025]` `cfg(target_os = "linux")` is false on Android**, whose `target_os` is `"android"`. Three sites therefore compile *differently* there and nothing checks it: `session.rs`'s I/O-priority code, `lib.rs`'s `peak_rss_bytes`, and the `alsa` dependency. `cfg(unix)` is true on both, which is why `director/program.rs` needs no change. This is the `libc` failure of 2026-09-22 in another form — code that compiles where it is written and differently where it runs (CLAUDE.md §10).

## 3. The changes, in order

The README ranks mobile *Future / Post-V1 (No early influence)*. `[GDE-HST-040]` to `[GDE-HST-070]` respect that: each is justified by `[REQ-HW-140]` — desktop hosts are first-class targets — or by a fault already found on the appliance, so none is wasted if the phone never happens. **`[GDE-HST-030]` does not**: an Android check in CI is the phone influencing the tree early, and it is taken now for `lempi-core` alone, deliberately, by `[GDE-HST-370]`. `[GDE-HST-080]` waits for Android work outright. The day counts are judgement, not measurement.

**`[GDE-HST-030]` An Android compile check, in the full run and in CI.** Start with `cargo check -p lempi-core --target aarch64-linux-android`, then widen to the player. It needs an image with the NDK, because `libsqlite3-sys` compiles C in its build script even under `cargo check` — too heavy for the pre-commit gate, right for `verify-targets.sh` and CI. Without it the target decays between work sessions, silently, exactly as `[GDE-HST-025]` describes. **Done for `lempi-core`, 2026-09-24**: `build/Dockerfile.android` (NDK r30, checked against Google's published SHA-1), stage E of `build/verify-targets.sh`, and the `android-core` CI job. It was proven to fail as well as pass — a `compile_error!` under `cfg(target_os = "android")` in core passed the Windows check and failed this one — and the SQLite it compiles is ELF64 AArch64, so the NDK's compiler, not the host's, did the work. Widening to the player waits for Android work `[GDE-HST-370]`.

**`[GDE-HST-040]` A library-level player host.** Move `engine_thread`'s wiring into the library behind a handle — start, command, snapshot, persist, shutdown — and make `lempi.rs`, `station.rs` and a future JNI layer all call it. It pays off now: **the MPD naming fault fixed in `e899a67` lived in exactly this code, and nothing tested it, because it sat in the binary's wiring rather than in the library.** `session.rs`'s own header says it exists so the two binaries "cannot drift apart on what 'start playing' means"; this finishes that job. The engine's `Command` enum already carries `Play`, `Pause` and `Persist`, which cover losing and regaining Android audio focus and `onStop`. It does **not** cover ducking: `SetVolume` saves the listener's volume through `remember_settings()`, so a duck through it would overwrite that setting `[GDE-HST-340]`. The decisions this needs are `[GDE-HST-300]` to `[GDE-HST-340]`. *~3–5 days.* **Done 2026-09-25 for `lempi`**: `player/src/host.rs` holds the engine thread, the tick loop, the MPD guest, the echo client and the web server behind `Player::start(Config)`, with `command`, `state`, `persist`, `wait` and `shutdown`; `lempi.rs` is its command line and a plain `fn main`. **`station.rs` deliberately does not use it**: it is a finite harness — a fixed set, a queue listing, a stop when idle, an underrun count — and a never-idle radio host would change what it tests; it already shares what is shared, through `Session`. `[GDE-HST-330]` (the Android context) and `[GDE-HST-340]` (ducking) wait for Android work.

**`[GDE-HST-050]` A host seam, reconciled with SPEC011.** SPEC011 — target design, not yet built — already specifies the sink half: `PathState.audible` is a `Tristate` that reads `Unknown` when it cannot be determined, `[SPEC-APS-090]` replaces the `wpctl` poll, `sudo` and `lempi-btctl` with D-Bus subscriptions, and `[SPEC-APS-070]` keeps the engine unable to block. So this change must not invent a second answer to "is it audible". Its own ground is what SPEC011 does not cover — restart, power-off, Wi-Fi, LED, I/O priority, peak RSS — behind an `appliance` feature. How the two divide is `[GDE-HST-350]`, and how the UI learns what a host lacks is `[GDE-HST-360]`. The present behaviour is still the argument: with no `wpctl`, `sink::current()` returns `known: false`, `path.rs` checks only `.dummy`, and on Windows, on any node without PipeWire and on a phone the "is it audible" guarantee disappears without a word — the silent skip `[GDE-DEP-060]` forbids and SPEC011's `Unknown` exists to prevent. *~2–4 days.*

**`[GDE-HST-060]` A `Snapshot` contract with a fixture.** It has 57 fields, and `fbui` already keeps its own hand-copied 11-field `ClientSnapshot`; a phone UI would be the third consumer. **Compatibility is judged by which fields are present, not by a number** — the rule `[SPEC-PL-065]` set for the payload, where a version is recorded and never consulted for acceptance. So the change is a fixture naming the fields each consumer requires, checked by Rust and by `fbui` the way `fixtures/fade/` is checked by Rust and `fade.js`. A `snapshot_version` may ride along for diagnosis, and only with a consumer that reads it at merge `[GDE-FBD-060]`. *~1 day.*

**`[GDE-HST-070]` A logging facade whose appliance output is byte-identical.** §4 below. *~1 day for the facade, then one module at a time.*

**`[GDE-HST-080]` When Android work starts, not before:** an audio-source resolver in place of every path §2's table lists, not only the decoder's; ducking, if a device shows it is needed `[GDE-HST-340]`; and a transfer hash in the payload, so on-device import can confirm a file arrived intact without re-deriving what it is. That is a separation `[SPEC-PL-075]` stops short of — today arrival is verified *by* the identity hash, which is why a phone would need ffmpeg. The alternative, moving the hash authority early, is `[SPEC-RLK-150]`'s and waits for its own reasons.

**`[GDE-HST-090]` Deliberately not yet: a `web` feature gating `axum` and `tokio`.** Whether it is wanted depends on `[GDE-AND-060]`: if the phone runs the existing skins in a WebView, the server stays. `[GDE-HST-310]` keeps that question from blocking `[GDE-HST-040]`.

## 4. Logging: `tracing`, and the constraints that decide whether it helps

**`[GDE-HST-100]` `tracing` is the right interface for the Rust code, and a better fit here than `log`.**

- **It is already compiled in.** `axum`, `axum-core` and `tower` depend on it, and nothing installs a subscriber, so their events currently go nowhere. Measured in the real graph, 2026-09-24: the player gains four crates (`tracing-subscriber` with `std` and `registry` only — no `fmt` — `tracing-log`, `sharded-slab`, `thread_local`), and core three (`tracing`, `tracing-core`, `pin-project-lite`; `once_cell` was already there) with `default-features = false`, which also avoids the proc-macro dependencies. None trips the boundary gate.
- **It captures what is being lost.** Every `symphonia` crate, and `tungstenite`, reports through `log`, and no `log` logger is installed — so the decoder's own warnings about malformed files are discarded today, in a project that spent a specification on stray bytes at the end of an MP3 `[SPEC-RLK-085]`. A subscriber with the `log` bridge keeps them, and names the crate each came from — a bare "invalid main_data offset" says nothing about where it arose — while this project's own lines are never attributed.
- **The lines are already records.** `clock: frames=151552 delay=24374 rate=44100 ts=Hardware callbacks=74` is structured data written out as a string, and a script greps it back apart. Fields are its natural form.
- **Spans suit the concurrency.** Engine thread, path supervisor, web server, echo client and generation jobs run at once, and the echo timing problems cross both threads and nodes.
- **Every target has a subscriber**, verified on crates.io: `tracing-journald`; `tracing-android` or `paranoid-android` for logcat; `tracing-oslog` for iOS; and `tracing_android_trace`, which puts spans into Perfetto.
- **Library discipline comes free.** Core emits and never installs; the host decides. With no subscriber an event is a cached check.

**`[GDE-HST-110]` The journal cannot tell a warning from a heartbeat.** Measured on `lempi02w`: 500 of the last 500 lempi lines at `PRIORITY=6`; `journalctl -p warning` returns nothing; six of the last 2,000 lines say *cannot*, *failed* or *error* — one of them `cannot name URIs for MPD`, the fault fixed in `e899a67`, sitting at the level of a clock tick.

**`[GDE-HST-120]` Constraint 1 — message text is a contract, and a narrow one.** One reader is strict: `build/verify-playing.sh` reads `journalctl -o cat` and anchors on `^clock: frames=`. Two are loose: `LempiPi/lempi-radio-test` and its identical twin `LempiPi/radio-silence-test.sh` match `error|recover` anywhere in a line, case-insensitively. `build/install-player.sh` and `BosePi/power-test-manifest.sh` only show lines to a person, and the latter's come from the start-up scripts, not the binary. Off the appliance, `build/deploy-local.sh` writes stdout to `lempi-local.log`. The default `fmt` output adds timestamps, levels, targets and fields and would break the strict reader. **A line a script reads keeps its message byte-identical; fields are added beside it, never substituted** — and a test pins `clock: frames=` and the two loose words.

**`[GDE-HST-130]` Constraint 2 — choose the destination by detection.** The low-risk path is already switched on, at least on `lempi02w`: its unit has `SyslogLevelPrefix=yes` — systemd's default, but `bose` and `lp3-wifi` were not checked. So a message-only formatter writing `<4>` or `<3>` at the start of a line gets a real priority and journald strips the prefix — `-o cat` unchanged, transport unchanged. **Info lines carry no prefix at all**: info is the stream's own priority (`SyslogLevel=6`), so an unprefixed info line is byte-identical to what `println!` wrote, and the strict `clock: frames=` reader sees no change on any node whatever its `SyslogLevelPrefix` says. Write the prefix only when `JOURNAL_STREAM` is set, which systemd does when stdout is the journal; otherwise a literal `<4>` lands in `lempi-local.log`. `tracing-journald`, which stores fields as journal fields, is a later step, because it moves the transport from stdout to the journald socket.

**`[GDE-HST-140]` Constraint 3 — nothing that writes may block the audio path, and the engine tick is part of it.** `fill()` in `output.rs` prints nothing today; the repository already counts in the callback and reports from the supervisor thread (`output: 1 missed ring lock(s)`). But `[GDE-FBD-090]` forbids any I/O on the engine tick `[SPEC-APS-070]`, and the tick already breaks it: `Engine::tick` begins with `drain_commands`, whose `echo-follow`, `echo-join` and `echo-rate` messages are `eprintln!`s. A subscriber writing to stdout would carry that forward. **The writer must not block its caller**: it hands lines to a worker thread through a bounded queue and, when the queue is full, drops rather than waits — and counts what it dropped, which the worker reports, because a lost line nobody counted is a silent success. That turns the migration into the fix for an existing breach rather than its continuation; which writer is `[GDE-HST-380]`. **Only a thread that marks itself uses the queue** — the tick thread, in each of the four binaries that run one, marked just before its loop. Every other thread writes synchronously, because a message written just before `process::exit` must not be lost in a queue the exit never drains, and that is how every binary reports a fatal error. The marked thread has the mirror problem when its loop ends and the program exits straight after, so each loop is followed by `logging::flush`, which unmarks the thread and waits up to half a second for the queue to empty: `play` on a missing file lost its `skipping` line in 0 of 20 runs with it, where without it the line's arrival was a race that happened to be won. Write both rules into `output.rs` and `engine/mod.rs`.

**`[GDE-HST-150]` Constraint 4 — filter with `Targets`, not `EnvFilter`.** Installing a subscriber surfaces `axum`, `tower`, `tungstenite` and `symphonia` at once. `tracing_subscriber::filter::Targets` filters by crate and needs only `std`; `EnvFilter` adds `matchers`, `regex-automata` and `regex-syntax`, measured — a memory decision against `[REQ-HW-100]`'s 150 MB.

**`[GDE-HST-160]` Not every `println!` is a log line.** Program output stays as it is: `build/deploy-appliance.sh` confirms a deploy by reading `lempi --version`. What migrates is diagnostics, and each migrated module locks itself with `#![deny(clippy::print_stdout, clippy::print_stderr)]`. Core goes first of the library — two sites — which also guarantees the library can never choose a phone's output for it. **The lock needs a gate that runs clippy**, and none did: the pre-commit gate ran `cargo check`, and the Linux image had no clippy. Both changed on 2026-09-24, and CI gained a clippy step; a planted `println!` in a locked module passed `cargo check` and failed the gate.

**`[GDE-HST-170]` "Throughout the system" ends at the language boundary.** Vipunen is Python — 952 `print()` calls, no use of `logging` — and is a separate process communicating with Lempi only through the shared database `[GDE-ARC-015]`. What can be shared across Rust, Python and shell is a **convention**: the level names, the `<N>` prefix under systemd, and the rule that a message a script reads is a contract. Vipunen never reaches the phone, so it is off this path.

**`[GDE-HST-180]` Order** — *steps (1) to (3) done 2026-09-24: every diagnostic in core and in the player's library goes through `tracing`, 79 sites across eleven modules, each locked; what prints directly is `cli.rs`, the command line's own output. Step (4), the binaries, is next* — with (1) and (2) swapped in practice, so that no commit leaves core's lines emitted into a process with no subscriber to write them. (1) Core: `tracing` without default features, the print lints, two sites. (2) Binaries: the subscriber, installed once in `cli::Spec::parse` so all seventeen get it — message-only stdout, `<N>` only under `JOURNAL_STREAM`, `Targets`, the `log` bridge, the non-blocking writer — then the `eprintln!`s that are real warnings first, since they are `[GDE-HST-110]`'s problem, and the prefix test. (3) The library's remaining sites of its 82, one module per commit: those are what a phone would otherwise lose. (4) The diagnostics among the binaries' 340 lines, likewise; never one diff (CLAUDE.md §1, §9). (5) Android: the host installs a logcat layer, and `tracing_android_trace` when measuring. (6) `tracing-journald` once the stdout path has proved itself.

**`[GDE-HST-190]` One dependency warning is expected, and is demoted — up to a point.** Deployed to `lempi02w`, the `log` bridge surfaced one symphonia message and no other: `mpa: invalid main_data_begin, underflow`, 9 of 9 dependency lines in 12 minutes, about one per passage start — some 45 warnings an hour, burying `journalctl -p warning` in exactly the noise `[GDE-HST-110]` set out to remove. It is the MP3 bit reservoir: a frame may borrow up to 511 bytes from the frames before it, and a start mid-file, which Lempi makes by design, means those frames were never decoded. At 128 kbps that explains at most two underflows per start; twelve measured starts showed zero, one or two. *Decided by the maintainer, 2026-09-25:* per opened file, the first **five** are written as info — still in the journal, not among the warnings — the sixth is written as a warning that says further ones are counted, and the rest are counted and reported once, when the file closes. A damaged file therefore costs two warning lines, not hundreds. Five rather than three because lower bitrates reach further back: about three frames at 64 kbps. The count belongs to the decoder, which makes it visible to the log layer only while it calls into symphonia, so a crossfade's two files never share one, and the same text outside a decode stays a warning. Verified with real symphonia output: a clean 128 kbps file started 5 s in produced 2 underflows, both demoted; a copy with 39 cuts produced 16 — five demoted, one surfaced, one summary. Matched on symphonia 0.5.5's exact text, so a reworded message fails towards noise, not silence.

## 5. Open

1. **`[GDE-HST-200]` The Director's rebuild cost is two different numbers, and battery wants the second.** `[IMPL-SUI-075]` measured `Director::load` at **9.86 s** in isolation with `dircheck`. In service on `lempi02w` — rebuilding while it plays, decodes and serves — the journal holds 17 rebuilds over the same 8,330 radio passages: **median 22.8 s, range 14.5–32.9 s** (2026-09-23/24). A phone's budget should be set against the in-service figure. An isolated re-run of `dircheck` on the node needs the player stopped and has not been done.
2. **`[GDE-HST-210]` `lempi02w`'s journal is over its cap and losing entries.** 71.6 MB against `SystemMaxUse=64M`; the whole of 2026-09-22 retains 221 lempi lines and none of the rebuilds observed that day. Levels and target filtering in §4 would reduce the volume, but the retention policy is its own decision — and until it is made, "the journal holds n of something" is a lower bound.
3. **`[GDE-HST-220]` The NDK image is large, and nothing has trimmed it.** Measured 2026-09-24: **5.48 GB**, 174 s to build the first time; the check itself runs in 16 s cold and 7 s warm. Most of the size is NDK content a compile check never touches — other architectures' toolchains, the sysroots of other API levels — and removing it is possible and unmeasured. It matters for CI's disk and download on every run, not for the result.

## 6. Decided

Each was put as a question with a recommendation and its reason; the maintainer accepted all nine recommendations on 2026-09-24, and `[GDE-HST-340]` was extended at acceptance to ramp both into and out of a duck. Implementing them is `[GDE-HST-040]` and `[GDE-HST-050]`'s work; recording them here is what keeps two implementers from building different things.

**`[GDE-HST-300]` Who owns the async runtime.** Today `lempi.rs` is `#[tokio::main]`; the engine, backup and tag scan run on plain threads, the echo client and web server on tokio. *Decided:* the library creates and owns its runtime inside `start()`, and the binaries become plain `fn main()`. A JNI caller has no runtime to lend, and a binary that kept `#[tokio::main]` while the library built another would nest them, which tokio refuses at run time.

**`[GDE-HST-310]` Whether `start()` starts the web server.** Upstream this is `[GDE-AND-060]`, and it is open. *Decided:* the configuration carries the server's address as an option — the binaries pass one, a native-UI phone passes none, a WebView phone passes localhost — so `[GDE-HST-040]` can be built before the WebView question is answered.

**`[GDE-HST-320]` Where configuration is resolved.** `[GDE-CLI-090]` resolves every option through four layers — command line, stored setting, environment, default — in one function in `cli`. *Decided:* the library takes an already-resolved configuration struct; `cli` stays with the binaries and keeps doing all four layers; a phone fills the same struct from its own settings screen and layer 2, which the library already reads from the listener database. "No binary and no option implements precedence" stays true, `[GDE-CLI-095]` holds naturally because paths are fields the host supplies, and the struct becomes the one list of what a player needs.

**`[GDE-HST-330]` Who gives cpal its Android context.** cpal's AAudio backend reads `ndk_context::android_context()`, and something must first call `ndk_context::initialize_android_context(vm, context)`. *Decided:* the JNI shim, before `start()`, because only it holds the `JavaVM` and `Context` — through one library function that wraps the call and records that it happened, so `start()` can refuse with a named error instead of letting cpal fail inside device enumeration.

**`[GDE-HST-340]` How ducking works.** Android asks a player to *duck* — keep playing, quieter — when another app speaks briefly, a navigation prompt for instance. Routing it through `SetVolume` is ruled out, because that command persists through `remember_settings()`: the duck would be saved as the listener's volume, a process killed while ducked would come back quiet, and restoring would need a second copy of the volume that a change made during the duck would silently undo. *Decided:*

- **A `SetDuck` command carrying a transient factor**, multiplied into the volume `fill()` already applies, never passed to `remember_settings()`, and 1.0 at every start — so the listener's volume and the duck never overwrite each other, and a process killed while ducked comes back at the listener's volume.
- **Applied at the output, where the volume is**, not upstream: the ring holds about 14 s, and gain applied on the way in lags by that much `[REQ-AUD-152]`. A duck that arrived after the prompt had finished would be no duck.
- **Ramped both ways, in and out.** `fill()` applies volume as one step per buffer — tolerable for a fader moved in small increments, not for a single jump of −14 dB, which clicks. The factor moves from where it is to where it is asked to go along a `fade::Curve`, looked up from a table built once as the skip fade's is (`fade_table`), not computed per sample in the callback. The ramp's position is carried from one callback to the next, and a `SetDuck` arriving mid-ramp starts from the factor currently applied, never from the previous target. Durations are named constants — 50 ms down and 250 ms back up to start, which is judgement, set by ear on a device.
- **Built with the Android work, not before** `[GDE-HST-080]` — nothing on the appliance or the desktop receives focus events — **and only if a device shows it is needed.** Android 8.0 and later can duck an app automatically; whether that reaches a `cpal`/AAudio stream is unverified. One test decides it before any code is written: Lempi playing, a navigation prompt spoken, listening for whether the music dips.

**`[GDE-HST-350]` How SPEC011 and the host seam divide.** *Decided:* SPEC011's supervisor is the only thing that answers "is it audible", and its observations arrive through one observer per platform — today's `wpctl` code on Linux, replaced by D-Bus per `[SPEC-APS-090]`; stream state on Android; nothing on Windows, which reads `Unknown`. The `appliance` seam holds only what SPEC011 does not. The smallest first step is the observer interface alone, with today's `wpctl` code as its Linux implementation and `Unknown` elsewhere, shaped as `PathState.audible` — so SPEC011's D-Bus observer later replaces an implementation rather than its callers.

**`[GDE-HST-360]` How the UI learns what a host can do.** The lempi skin posts `/power/restart` (`player/src/web/skins/lempi/skin.js`), and gating the power, Wi-Fi, LED and radio routes behind `appliance` would leave buttons that answer 404. *Decided:* the snapshot declares the host's capabilities — restart, power-off, Wi-Fi, Bluetooth — the way `Playback::Capabilities` declares a backend's `[SPEC-BK-040]`, and the skins hide what is absent. Its consumer at merge is the skins `[GDE-FBD-060]`, and it belongs in `[GDE-HST-060]`'s fixture.

**`[GDE-HST-370]` Whether to take `[GDE-HST-030]` before Android work starts.** The README's "No early influence" argues against; `[GDE-HST-025]` argues for — code gated on `target_os = "linux"` compiles differently on Android, and nothing notices until the day it matters. *Decided:* take it now for `lempi-core` only, the crate already built to be portable, and amend the README's row to say so; widen to the player when Android work begins.

**`[GDE-HST-380]` Which non-blocking writer.** `tracing-appender` 0.2.5 does what `[GDE-HST-140]` needs — a worker thread, lossy when full, an `error_counter()` — but adds 15 crates, among them a date library and a rolling-file appender this project would not use, and buffers up to 128,000 lines by default. The alternative is about forty lines over `std::sync::mpsc::sync_channel`: bounded, non-blocking on `try_send`, a counter of drops. *Decided:* the forty lines, with a small bound — no new crate, a buffer sized for the appliance rather than for a server, and a drop count that is ours to report. **Built 2026-09-24** in `player/src/logging.rs`: a queue of 1,024 lines, a `lempi-log` writer thread that wakes at least once a second so a drop is reported even when nothing follows it, and a queue used only by marked threads `[GDE-HST-140]`.
